# 系统主面板材质：调研结论与接入方案

调研时间：2026-11-07。这里的“主面板”指 Windows 系统隐藏图标区，TrayNest 的自选收纳面板保持独立。

## 结论

有可参考的实现路线：进入 Explorer 的 XAML 层，修改背景控件的 `Background` 画刷。窗口级透明属性不是本机这个面板背景的有效修改入口。

Windhawk 官方样式指南给出的目标是 `Border#OverflowFlyoutBackgroundBorder`；其模组源码还提供带父级约束的完整匹配：`SystemTray.NotificationAreaOverflow > Grid#OverflowRootGrid > Border#OverflowFlyoutBackgroundBorder`。源码包含对该控件使用 AcrylicBrush 的实际样式。依据：[官方指南](https://github.com/ramensoftware/windows-11-taskbar-styling-guide#tray-overflow-background)、[模组源码，固定提交](https://github.com/ramensoftware/windhawk-mods/blob/7a2157258d4698ee9eb809ea45719051a62ed99a/mods/windows-11-taskbar-styler.wh.cpp#L1852)。这个名字仍属于 Windows 内部界面实现，需在目标系统上实际匹配，不能当成长期稳定的系统接口。

## 三条路线

| 路线 | 结论 | TrayNest 的用途 |
|---|---|---|
| 对隐藏区 HWND 设置 DWM / accent 属性 | 本机试验不能改变内部背景，还可能改变宿主透明边缘 | 已撤回产品实现；不继续作为同步方案 |
| 使用 Windhawk Taskbar Styler 定点修改背景 | 有现成的主面板样式规则，需要外部运行环境 | 可用于验证目标和视觉参数，不要求所有用户安装 |
| 自带小型原生 XAML 桥接 DLL | 接入成本较高，但可以由 TrayNest 管理启用、更新和恢复 | 建议作为产品方案；保留现有 C# 主程序 |

用户已选择自带桥接方案；preview.12 已实现，并在本机 Windows 11 25H2 验证。设置中的“统一两个面板的材质”负责启用和关闭，不需要外部美化工具。

## 桥接为什么可行

微软的 `InitializeXamlDiagnosticsEx` 文档明确提供目标进程 ID、待加载 DLL 和实现 `IObjectWithSite` 的 COM 类；运行时提供 `IXamlDiagnostics`。这是调试诊断接口，能访问 XAML 树，并不代表微软承诺系统隐藏区控件结构稳定。[微软接口文档](https://learn.microsoft.com/en-us/windows/win32/api/xamlom/nf-xamlom-initializexamldiagnosticsex)

TranslucentTB 的 ExplorerTAP 接收诊断站点、监听视觉树，然后在目标线程修改画刷。其现成服务针对任务栏背景和边框，不能直接宣称支持隐藏区；TrayNest 仍需实现上面的隐藏区目标匹配。[站点初始化](https://github.com/TranslucentTB/TranslucentTB/blob/d4636e439865df0a1a1419db408e055740ce5c74/ExplorerTAP/tapsite.cpp)、[视觉树监听](https://github.com/TranslucentTB/TranslucentTB/blob/d4636e439865df0a1a1419db408e055740ce5c74/ExplorerTAP/visualtreewatcher.cpp)

UWPSpy 可用于实机查看、试改 XAML 元素属性；项目说明也明确使用 XAML Diagnostics。因此它适合做控件定位验证，不是最终安装包必须附带的依赖。[UWPSpy 项目说明](https://github.com/m417z/UWPSpy/blob/d959bec865801731dc6474fe5786264463b7596e/README.md)

## TrayNest 的具体接法

1. C# 管理设置和状态；一个职责有限的 x64 原生 DLL 管理目标控件和画刷，优先评估 C++/WinRT。无需为这个功能重写整个软件。
2. 只接受所属 Explorer 和隐藏区根节点均匹配的背景控件。修改背景，不重建图标列表，不接管图标输入，不修改全局资源字典或系统主题。
3. 共用外观配置：浅色和深色使用实色画刷；亚克力使用 XAML AcrylicBrush。开启同步时，“跟随系统托盘”使用随系统明暗变化的亚克力；关闭同步时清除自定义覆盖并恢复原背景。
4. WinForms 的 accent 配方与 XAML AcrylicBrush 不是同一套参数，透明度数字不能直接照搬。先统一颜色、透光和模糊的视觉目标，再用相同背景下的双面板截图校准。
5. 挂接成功、找到目标、应用完成分别返回状态。初始化应异步、有超时；拖动或右键操作期间延后材质变更。
6. 记录原始本地属性状态。关闭同步或退出时恢复原值；原先没有本地值的属性应清除覆盖，让系统继续处理主题资源。需要额外验证主题切换后的恢复行为。
7. 桥接独立监听 TrayNest 进程结束，即使主程序异常退出，也能回到系统背景。Explorer 重建控件后重新匹配，避免长期持有失效对象。

第 6、7 点可参考 TranslucentTB 保存原始画刷、等待主进程结束、切回 XAML 线程恢复的实现；本项目不能只在正常退出函数中做一次恢复。[恢复与进程监听源码](https://github.com/TranslucentTB/TranslucentTB/blob/d4636e439865df0a1a1419db408e055740ce5c74/ExplorerTAP/taskbarappearanceservice.cpp)

## 必须验证的边界

- 有些任务栏美化工具会拦截其他 XAML Diagnostics 会话。Windhawk 当前源码甚至存在拦截后返回成功的分支；所以必须验证目标命中和实际画刷，不能只检查接口返回值。[相关源码](https://github.com/ramensoftware/windhawk-mods/blob/7a2157258d4698ee9eb809ea45719051a62ed99a/mods/windows-11-taskbar-styler.wh.cpp#L20656)
- 在 XAML 所在线程变更属性；避免让 Explorer UI 线程同步等待 TrayNest，重现之前的拖动互等问题。
- 扩展到浅色、深色、透明效果关闭、高对比度、省电、主题切换、隐藏区关闭重开、拖动中改设置、主程序异常退出和 Explorer 重建场景。
- 动态加载 DLL 的升级和卸载行为需单独验证；不能默认模块随开关关闭就卸载，也不能为了更新材质自动结束 Explorer。
- 外观“相同”的验收应依赖截图和交互表现；接口成功、JSON 保存成功不够。
- 当前 TrayNest 为 MIT；上述参考项目或模组标注 GPLv3。复用前需单独核对依赖和许可处理，不把示例源码当作无条件可复制的实现。

## 实现与验证

早期窗口属性原型未能改变内部背景，相关失败截图保留在 `verification/preview11/`。当前实现使用独立编写的原生模块，源码位于 `src/TrayNest.NativeBridge/`，通过 `IVisualTreeService3` 和 `IVisualTreeServiceCallback2` 定位背景；不复用 GPL 项目的实现代码。

自有 XAML 宿主已验证明显测试颜色、浅色、深色、亚克力及原背景精确恢复；模拟控制进程异常结束后也能恢复。真实 Explorer 的浅色、深色和亚克力已实际应用并截图，关闭同步前后采样背景亮度一致。证据位于 `verification/native-bridge/`，完整设置、自动展开、拖动与对齐检查位于 `verification/preview12/`。

亚克力使用 Backdrop，并显式设置较低的色调和亮度不透明度。试用 HostBackdrop 时新画刷退化为纯色，已通过实拍纠正。两个面板分别使用 XAML 与 WinForms 绘制，材质类型及配色一致，但不承诺每个像素完全相同。

关闭同步或正常退出会恢复原始本地背景值；桥接还监听所属 TrayNest 进程结束并在 XAML 线程恢复。若其他美化程序已替换背景，不覆盖它的新画刷。DLL 从用户缓存加载，以内容摘要区分版本，关闭开关不会强制卸载模块，也不会为更新而重启 Explorer。

目前没有覆盖所有 Windows 构建、第三方任务栏工具、高对比度、省电和 Explorer 异常重建组合；这些仍属于兼容性验证范围。连接失败不能以初始化接口返回成功代替目标和应用确认。
